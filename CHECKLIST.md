## Інфраструктура і деплой

Схема (рішення від 2026-09-06): бекенд у хмарі — **stateless**, байти файлів
лишаються фізично на домашньому ПК, браузер ходить за ними напряму.

```
Браузер ──статика──► Cloudflare Pages
        ──API───────► Render (ASP.NET у Docker)
        ──байти─────► домашній ПК: Garage (S3) за тунелем
```

### Файловий сервер удома

- [ ] Підняти **Garage** у Docker (S3-сумісний, Rust, під self-host).
      Не MinIO: community-репозиторій архівовано в лютому 2026 — без патчів безпеки
- [ ] Дані — у volume на диску, щоб переживали перезапуск контейнера
- [ ] Тунель для публічного HTTPS: **Tailscale Funnel** (`*.ts.net`, домен не потрібен)
      або Cloudflare Tunnel (потребує власного домену на їхніх NS)
- [ ] Ключі доступу (access key / secret) — у змінних оточення Render
- [ ] **CORS на самому бакеті** — окремий конфіг Garage, не `AddCors` у ASP.NET.
      Браузер вантажить на інший origin, і дозвіл видає сховище. Класичне місце,
      де застрягають
- [ ] Фронт має пережити недоступність сховища: ПК вимкнено → API живий і віддає
      списки, а байти не тягнуться

      завантаження не гонились). Ендпоінт більше не знає про файлову систему — віддає

      під GUID у `data/assets`
- [ ] `S3AssetStorage` (`AWSSDK.S3`) другою реалізацією; перемикання — реєстрацією в DI
      за конфігом
- [x] Прибрати захардкоджений `ContentRootPath` з `Program.cs` — шлях тепер із конфігу
      (`Storage:AssetsPath`, дефолт `data/assets`) і резолвиться всередині
      `LocalFileAssetStorage`; абсолютний шлях у конфізі береться як є. S3-реалізації

### Бекенд у хмарі

- [x] Multi-stage `Dockerfile` у корені репо: `node:24-alpine` збирає фронт,
      `sdk:8.0-alpine` — бекенд, `aspnet:8.0-alpine` виконує; `dist` лягає у `wwwroot`.
      Render не має нативного .NET-рантайму — тільки Docker.
      Зібрано локально (`docker build -t knowledgebase:local .`) — 163 МБ, без помилок;
      контейнер запущено як на Render (`-e PORT=10000`) і прогнано весь набір перевірок:
      `/` і `/notes` → 200 `text/html`, `/assets/*.js` → 200 `text/javascript`,
      `/health` → 200, `/api/does-not-exist` → 404, логін/`me`/upload → 200,
      без cookie → 401. `/swagger` у Production → 404, як і має бути
- [x] Kestrel слухає порт зі змінної `PORT` (Render передає свій). Перевірено:
      `PORT=8099 dotnet Backend.dll` → `Now listening on: http://[::]:8099`
- [x] `ForwardedHeaders` **перед** `UseHttpsRedirection` — за проксі інакше
      виходить цикл редіректів. Перевірено на Production-білді: запит із
      `X-Forwarded-Proto: https` віддає 200, без нього — 307 на `https://`.
      Побічно підтвердилось прапорцем `secure` в `Set-Cookie` (політика
      `SameAsRequest` бачить схему саме із заголовка)
- [ ] **Персистувати ключі Data Protection.** Ними шифрується вміст auth-cookie,
      за замовчуванням вони лежать на диску — а диск Render ефемерний. Наслідок:
      кожен деплой розлогінює. Виглядає як плаваючий баг, а це конфігурація.
      На Free полагодити нічим: **диски доступні лише на платних інстансах.**
      Або платний план і `PersistKeysToFileSystem` на змонтований диск, або живемо
      з розлогіном після кожного деплою.
      Підтверджено на локальному контейнері. Сам ASP.NET пише про це в лог на старті:
      `Storing keys in a directory '/root/.aspnet/DataProtection-Keys' that may not be
      persisted outside of the container`. Перезапуск **того самого** контейнера
      (`docker restart`) сесію зберігає — ключі лежать у його шарі; а на **новому**
      контейнері, що й відбувається при деплої, стара cookie дає 401
- [x] Віддача зібраного фронту з ASP.NET (`UseStaticFiles` + fallback на `index.html`) —
      тепер **передумова авторизації**, а не косметика: одна адреса означає, що cookie
      одразу налаштовуються в остаточному вигляді. CORS у проді не потрібен узагалі.
      Перевірено: `/` і глибоке посилання `/notes` → 200 `text/html`, `/assets/*.js` → 200.
      Фолбек навмисне подвійний: `MapFallback("/api/{**path}")` віддає 404, бо
      суцільний catch-all відповідав би на друкарську помилку в шляху API сторінкою
      `index.html` зі статусом 200, і `fetch()` прочитав би розмітку як успіх
- [ ] Якщо колись фронт і API роз'їдуться на різні адреси — список дозволених origin
      брати з конфігу, не хардкодити (актуально лише для того сценарію)
- [x] Створити сам Web Service на Render: runtime Docker, `Dockerfile` у корені,
      гілка `main`. Задеплоєно: <https://knowledgebase-9z29.onrender.com/>.
      Перевірено на живій адресі: `/` і `/notes` → 200 `text/html`, `/assets/*.js` → 200,
      `/health` → 200 `Healthy`, `/swagger` → 404, `/api/nope` → 404,
      `me` без cookie → 401, невірний пароль → 401, вірний → 200 з
      `Set-Cookie ... secure; samesite=lax; httponly`, `me` з cookie → 200,
      logout → 204. `http://` → 301 на `https://` віддає edge Render, ще до застосунку
- [ ] Врахувати, що Free-інстанс **засинає після 15 хв без трафіку**, підйом ~1 хв.
      Перший запит після паузи виглядатиме як зависання
- [ ] Ефемерна файлова система з'їдає ще й `data/assets`: завантажені файли зникають
      при кожному деплої. Перевірено на контейнері — файл, залитий через
