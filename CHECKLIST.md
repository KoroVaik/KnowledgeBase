      Content-Type при віддачі вгадується з розширення (`FileExtensionContentTypeProvider`).
      Перевірено curl'ом на **обох** провайдерах — `Local` і `S3` (Garage):
      login → список → upload (`201`, `Location`) → скачування (байти ті самі) →
      `DELETE` (`204`) → повторний `DELETE` (`404`) → скачування після видалення (`404`);
      неіснуюче ім'я `404`, `..%2F..%2Fappsettings.json` і `%2E%2E%5C...` → `404`,
      без cookie `401`, порожній файл `400`. Через Vite proxy (`localhost:5173`) —
      теж `201`. Тека `data/assets` після прогону чиста

      для фронту (анонімний — екран логіну має знати стан до входу).
      Перший прапорець — `Features:UploadEnabled`, зараз `false`: завантаження
      вимкнено. Заборона стоїть **в `AssetsController.Upload`** (`403`), а не тільки
      в UI — заблокована кнопка є підказкою, а не обмеженням; curl'ом її нема.

      перечитується на кожен запит, тож прапорець перемикається правкою
      `appsettings.json` без перезапуску. На Render — `Features__UploadEnabled`.
      Фронт до відповіді `/api/features` вважає фічу **вимкненою**: показати робочу
      кнопку, яку сервер потім відкине, гірше, ніж на мить показати заблоковану.
      `readOnly` на `<input type="file">` браузер ігнорує, тому саме `disabled`.
      Другий прапорець — `Features:DownloadEnabled` (зараз `true`): гейтить
      `GET /api/assets/{fileName}`, і при `false` ім'я файлу в списку рендериться
      текстом замість `<a href>`. Два напрямки — два прапорці: upload це від
      користувача на сервер, download — назад до нього

      і клікати синтетичне посилання.

      завантажень, який форма інкрементує після успіху, а список тримає в залежностях
      ефекту. Після видалення рядок прибирається з локального стану, без повторного
      `GET`. Перезавантаження списку навмисне лишає старі рядки на екрані замість
      «Loading…» — інакше таблиця блимала б після кожного завантаження.
      Перевірено в браузері (субагент, dev-сервери): вхід → таблиця з двома наявними
      файлами, розміри `78.4 KB`/`321.4 KB`, новіші зверху → upload `201` і рядок
      з'явився сам, без перезавантаження сторінки → клік по імені `GET` `200`
      з `Content-Disposition: attachment` → `confirm` показує ім'я файлу →
      `DELETE` `204` і рядок зник без перезавантаження → скасування `confirm`
      не шле запиту взагалі → після `F5` список рендериться, сесія жива

## Інфраструктура і деплой

Схема (рішення від 2026-09-06): бекенд у хмарі — **stateless**, байти файлів
лишаються фізично на домашньому ПК, браузер ходить за ними напряму.

```
Браузер ──статика──► Cloudflare Pages
        ──API───────► Render (ASP.NET у Docker)
        ──байти─────► домашній ПК: Garage (S3) за тунелем
```

### Файловий сервер удома

- [x] Підняти **Garage** у Docker (S3-сумісний, Rust, під self-host).
      Не MinIO: community-репозиторій архівовано в лютому 2026 — без патчів безпеки.
      `infra/garage/`: compose з образом `dxflrs/garage:v2.3.0`, `garage.toml`,
      секрети в `.env` поза git, bootstrap-команди в `README.md`.
      Порти 3900/3903 прив'язані до `127.0.0.1` — назовні нічого не стирчить,
      поки перед Garage не поставлено тунель. Бакет `knowledgebase-assets`,
      ключ `knowledgebase-backend` з правами RW.
      `rpc_secret`/`admin_token` навмисне в env, а не у файлі конфігу: bind-mount
      на Windows виглядає для Garage world-readable, і він відмовляється стартувати.
      `root_domain` у `[s3_api]` не заданий — vhost-style вимагає wildcard-DNS,
      якого жоден тунель не дає, отже лишається тільки path-style.
      Перевірено round-trip'ом через одноразовий `amazon/aws-cli`: put → list → get,
      файл побайтово той самий
- [x] Дані — у volume на диску, щоб переживали перезапуск контейнера. Перевірено
      сильнішим тестом, ніж restart: `docker compose down` + `up` (контейнер
      створюється наново) — об'єкт на місці
- [x] Тунель для публічного HTTPS: **Tailscale Funnel** (`*.ts.net`, домен не потрібен).
      Cloudflare Tunnel відкинуто: вимагає власного домену на їхніх NS і має ліміт тіла
      запиту 100 МБ на Free. `tailscale funnel --bg 3900` →
      `https://rospc.tail11818d.ts.net` (443) → `127.0.0.1:3900`. Прив'язку Garage до
      loopback не чіпали — Funnel ходить із того самого хоста.
      Дозвіл вмикається атрибутом вузла (`nodeAttrs` + `funnel`) у політиці tailnet:
      візуальний редактор правил його не показує, тільки JSON editor. Плюс
      HTTPS Certificates на сторінці DNS.
      Перевірено ззовні: без ключів → 403 (відповідає Garage, а не тунель); put/list з
      ключами → працює; **presigned GET → 200 і побайтово той самий файл**, тобто Funnel
      не підміняє `Host`, на якому тримається підпис SigV4.
      Хостнейм публічний і знаходиться через Certificate Transparency — захист сховища
      тримається виключно на ключах
- [x] Окремий ключ для прода — `knowledgebase-render` (RW на бакет), щоб у хмарі був не
      той самий ключ, що в локальному `appsettings.Local.json`: відкликаються нарізно
- [x] Ключі доступу (access key / secret) — у змінних оточення Render
      (`Storage__Provider=S3`, `Storage__S3__*`). Сховище на проді працює — за словами
      користувача (2026-09-07): upload на `knowledgebase-9z29.onrender.com` доходить
      до Garage. Тобто `S3AssetStorage` підтверджено не лише проти локального Garage,
      а й у зв'язці Render → Tailscale Funnel → домашній ПК
- [x] **CORS на самому бакеті** — окремий конфіг Garage, не `AddCors` у ASP.NET.
      Браузер вантажить на інший origin, і дозвіл видає сховище.
      Правило в `infra/garage/cors.json`: тільки `PUT`, тільки з `http://localhost:5173`,
      тільки заголовок `content-type`. Ставиться через S3 API (`PutBucketCors`) — окремої
      команди в `garage bucket` немає. **Пастка:** RW-ключа замало, зміна конфігурації
      бакета вимагає прав owner, інакше `AccessDenied: Operation is not allowed for this
      key`. Owner видано на час правки і одразу знято — бекенду він у роботі не потрібен.
      Перевірено з реальної сторінки: `fetch` PUT з `http://localhost:5173` → 200,
      **той самий підписаний URL** з `http://localhost:5244` → `TypeError: Failed to
      fetch`, тобто блокує саме CORS, а не підпис. Preflight `OPTIONS` окремо: з дозволеного
      origin → 200 з `access-control-allow-methods: PUT`, з чужого → 403
- [ ] Фронт має пережити недоступність сховища: ПК вимкнено → API живий і віддає
      списки, а байти не тягнуться

### Абстракція сховища

- [x] `IAssetStorage` + `LocalFileAssetStorage` — інтерфейс і локальна реалізація за ним,
      зареєстровані в DI (singleton: теку створює конструктор, щоб паралельні перші
      завантаження не гонились). Ендпоінт більше не знає про файлову систему — віддає
      `Stream` і отримує `StoredAsset`. Перевірено реальним завантаженням: 200 і файл
      під GUID у `data/assets`
- [x] `S3AssetStorage` (`AWSSDK.S3` 4.0.102.5) другою реалізацією; перемикання —
      `Storage:Provider` = `Local` | `S3`, одним `if` у `StorageRegistration`.
      Ключі — лише через змінні оточення / user-secrets (`Storage__S3__AccessKeyId`);
      неповний конфіг валить застосунок на старті (`ValidateOnStart`), а не на першому
      завантаженні у вигляді 500. Іменування файлу винесено в `AssetFileName`, щоб
      `SafeExtension` не дублювався у двох реалізаціях.
      **Пастка AWS SDK v4:** дефолт `RequestChecksumCalculation = WHEN_SUPPORTED`
      перетворює PUT на chunked-тіло з трейлером контрольної суми, і Garage відповідає
      `Invalid payload signature`. Виставлено `WHEN_REQUIRED` у конфізі клієнта.
      Перевірено проти локального Garage: логін → upload → 200, об'єкт у бакеті
      побайтово збігається з надісланим; порожній файл → 400, без cookie → 401;
      `Provider=Local` поводиться як раніше
- [x] Локальні налаштування — `backend/appsettings.Local.json` (`UseLocalOverrides`):
      у `.gitignore` і `.dockerignore`, підключається **лише в Development**. Джерело
      додається після `CreateBuilder`, тому перебиває всі інші, включно зі змінними
      оточення — гейт на Development саме для цього: копія, що осіла поруч із
      бінарником, не перебʼє конфіг Render. Перевірено: ключі Garage лежать у файлі,
      `Storage__Provider=S3 dotnet run` вантажить у бакет без жодної змінної з ключами;
      без цієї змінної файли лягають у `data/assets`, як раніше; той самий файл поруч
      із бінарником у Production ігнорується (падіння на `ValidateOnStart`);
      `docker build` не бачить його в контексті (перевірено пробним образом)
- [x] **Postgres + EF Core під метадані файлів.** Новий зріз `Infrastructure/Persistence/`:
      `AssetRecord`, `KnowledgeBaseDbContext`, `AddDatabase`/`MigrateDatabase`; рядок
      підключення — `ConnectionStrings:Database`, міграції накатуються на старті.
      Спершу був SQLite (`data/app.db`) — відпав, щойно з'ясувалось, що на free-плані
      Render контейнер щодеплою чистий і диска під файл бази там немає взагалі.
      Локально Postgres у Docker (`infra/postgres`, той самий рушій, що в проді),
      у хмарі — Neon. EF Core, а не Dapper — заради міграцій.
      **Таблиця стала джерелом правди**: `GET /api/assets` читає її, а не сховище;
      `IAssetStorage` лишився відповідальним тільки за байти. Порядок операцій обрано
      під відсутність спільної транзакції: upload — спершу байти, потім рядок
      (сирота-файл невидимий, але нешкідливий), delete — спершу рядок, потім байти.
      `SaveChangesAsync` навмисно без `cancellationToken`: клієнт, що відвалився, не має
      коштувати рядка, без якого вже збережені байти стають невидимими.
      Перевірено curl'ом проти локального Postgres: upload → рядок у таблиці
      (`psql`: `Assets` + `__EFMigrationsHistory`, `UploadedAtUtc` типу
      `timestamp with time zone`), список з `originalFileName`, скачування під
      оригінальним іменем, `DELETE` → 204 і зникнення файлу з диска, повторний → 404.
      Раніше те саме пройдено на SQLite, разом із виживанням рядків після рестарту.
      **Пастка SQLite, через яку і зʼявився обхід:** він не сортує `DateTimeOffset`
      у `ORDER BY`, а `DateTime` віддає з `Kind.Unspecified` — тобто без `Z` у JSON,
      і браузер читав би UTC як локальний час. Лікувалось конвертером у моделі;
      у Postgres не потрібне взагалі — там `timestamp with time zone`
- [x] Рядок збирає фабрика `AssetRecord.For` — приймає окремі значення, а не `IFormFile`:
      записи скоро створюватиме AI-пайплайн, куди HTTP-запит не приходить. Порожнє ім'я
      підміняється збереженим, порожній MIME — `application/octet-stream`. Перевірено
      завантаженням файлу без розширення і без Content-Type: рядок і скачування коректні
- [x] Оригінальне ім'я і MIME-тип тепер зберігаються — закрилось усе, що з цього тягнулось:
      список показує «my report.pdf», `Content-Disposition` віддає файл під тим самим
      іменем (`filename*=UTF-8''my%20report.pdf`), `confirm` перед видаленням питає про
      впізнаваний файл. `Content-Type` при віддачі береться з рядка, а не вгадується з
      розширення — `FileExtensionContentTypeProvider` прибрано з контролера
- [ ] `GET /api/assets/{fileName}` при `Features:DownloadEnabled=false` віддає **406**,
      а не 403: на дії стоїть `[Produces("application/octet-stream")]`, а гілка з
      вимкненим прапорцем повертає JSON-обʼєкт, і узгодження типів провалюється.
      Спливло під час перевірки R2 — довелось вмикати прапорець змінною, щоб узагалі
      дійти до байтів
- [x] Content-Type самого об'єкта закрито разом із прямим доступом: у підписаному PUT
      тип **входить у підпис**, тож браузер зобов'язаний надіслати саме його, і об'єкт лягає
      в бакет уже з правильним типом. Для об'єктів, залитих раніше, тип і ім'я підставляються
      в момент видачі посилання через `ResponseHeaderOverrides`, тобто джерелом лишається
      таблиця. `IAssetStorage.SaveAsync` (старий шлях через бекенд) як не приймав тип, так і
      не приймає — на нього це вже не впливає
- [x] **Прод без стану — зроблено.** Контейнер на Render більше не зберігає нічого:

- [x] Рядок підключення заведено. Пастка на цьому шляху виявилась подвійна.
      **Перша:** Npgsql не розуміє URL-формат, у якому Neon віддає `DATABASE_URL`
      (`postgresql://user:pass@host/db`) — ADO.NET хоче `ключ=значення`. Перевірено
      окремою пробою: `NpgsqlConnectionStringBuilder` на такому рядку кидає
      `ArgumentException`. Перекладено руками у

      змінна з ключем `Host` замість `ConnectionStrings__Database`, і застосунок упав
      на старті. Рядки з `=` у значенні додавати тільки по одному, руками.
      Локально це й далі `appsettings.Development.json` з Postgres у Docker: про

## AI-пайплайн

Схема (рішення від 2026-09-09). Завантажений файл → рядок `AssetRecord` → рядок у
черзі `ProcessingJobs`. Воркер опитує чергу, бере байти з бакета напряму (він серверний,
ключ у нього є — presigned не потрібен), віддає моделі, пише `Note` + `NoteLink` у
Postgres. Тіло нотатки — колонка `text`, не `.md`-файл (див. CLAUDE.md).

- **Воркер** — окремий процес `KnowledgeBase.Worker` (розділено 2026-09-09). Живе на
  домашньому ПК поряд з Ollama, ходить у Neon і R2 по інтернету. У прод (Render) їде
  тільки `KnowledgeBase.Api`. Прапорець `Pipeline:Enabled` **не робимо** — після
  розділення API воркера не хостить, а воркер завжди має крутити цикл, тож вимикати
  нема чого.
- **Черга — таблиця Postgres**, не зовнішній брокер (правило «без окремого сервісу»).
  Вибірка `SELECT ... FOR UPDATE SKIP LOCKED`.
- **Фронт** пінгає `GET /api/notes` на завантаженні сторінки; бек читає з БД те, що
  встиг обробити воркер. SSE-мосту воркер→бек поки нема (воркер на іншій машині не
  докличеться до `IChangeNotifier` у памʼяті).

## Фронтенд

- [x] **Падіння беку видно на сторінці.** Симптом один («сторінка показує актуальне, хоча API мертвий»), а місць три:
      1) `api/realtime.ts` тепер тримає стан з'єднання і роздає його через
      `subscribeToConnection`. `paused` — свідоме закриття (схована вкладка, простій
      15 хв, нема підписників), банер на нього не реагує; `offline` — будь-який
      `onerror`, **включно з тим, коли браузер ретраїть сам** (`readyState` =
      `CONNECTING`): для сторінки це така сама відсутність зв'язку. Заразом `sync()`
      закриває і відкладений реконект, інакше стрім, якого ніхто не хоче, лишався б
      у стані `offline`. Хук `useConnectionStatus` + банер в `App`.
      2) Холодний старт із мертвим API більше не кидає фронт у `anonymous` — це була
      брехня: показувалась форма входу, хоча входити нікуди. Новий стан `unreachable`
      з кнопкою «Try again». Ознака не «мережева помилка», а «`fetchCurrentUser`
      кинув»: `null` він віддає лише на 401, тож будь-який виняток означає «про сесію
      нічого не відомо».
      3) `apiFetch` в `api/http.ts` перекладає відмову `fetch` у `ApiUnreachableError`.
      `fetch` кидає лише коли відповіді не було взагалі, і текст у нього свій у кожному
      рушії — «Failed to fetch» перед користувачем бути не має.
      Перевірено в браузері, усі чотири сценарії: бек убито при відкритій сторінці —
      банер за ~3 с; бек піднято — банер зник сам, стрім перепідключився (у мережі видно
      4 × 502 через Vite-проксі, тобто спрацював саме шлях `CLOSED` + backoff, а не
      власний ретрай браузера); холодний старт із мертвим беком — екран
      `Could not read the session (HTTP 502)` з кнопкою, і «Try again» після підняття
      беку повернув сесію та список; схована вкладка — стрім закрився через 30 с
      (`ERR_ABORTED` у мережі), банер **не** з'явився, на поверненні стрім відкрився знову

- [x] **Смужка прогресу при завантаженні файлу.** Кнопка показувала лише «Uploading…»,
      без ознак руху. `putToBucket` (`api/assets.ts`) переведений з `fetch` на
      `XMLHttpRequest`: `fetch` принципово не віддає прогрес відвантаження тіла запиту,
      події `progress` є тільки в `xhr.upload` (`lengthComputable`, `loaded`, `total`).
      Прогрес рахується саме на `PUT` у бакет — два кроки на API (`upload-link`,
      `confirm`) дрібні, поки вони йдуть, стан прогресу `null` і `<progress>` без `value`
      (нативний невизначений вигляд). Контракт помилок збережений дослівно; заголовок
      лишився рівно один (`Content-Type`), інакше поламався б CORS-preflight бакета.
      `UploadState` у `FileUploadForm` розширений полем `progress`, текст кнопки —
      «Uploading… 45%», стилі `.upload-progress` в `App.css`. `build` + `lint` зелені.
      **Браузерну перевірку лишає користувач** — тут не запускалось; на локалхості смужка
      очікувано стрибне одразу на 100%, справжній рух видно на великому файлі в R2

- [ ] **Повернення на вкладку не давало видимої реакції.** Схована/простояла вкладка на
