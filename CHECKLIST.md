## Автентифікація

Рішення від 2026-09-06: скасовує попереднє «автентифікації немає і не планується».
Це **передумова деплою** — без неї публічний URL означає відкритий доступ до нотаток
і анонімний upload. Робиться першою, до інфраструктури нижче.

- [x] Механізм обрано: cookie-сесія, пароль з конфігу. Джерело identity відчеплене
      від сесії — GitHub OAuth другим кроком замінить лише endpoint логіну
- [x] Ліміт входу: 5 **невдалих** спроб за хвилину, окремо для кожної адреси-джерела.
      Керується вручну, а не middleware — той витрачав би спробу на кожен запит,
      включно з вдалим входом. Перевірка стоїть **до** звірки пароля, тож вичерпаний
      ліміт не дає підбирачу жодного зворотного зв'язку. 429 несе текст причини в тілі
- [x] `POST /api/auth/login`, `POST /api/auth/logout`,
      `GET /api/auth/me`; `/api/notes/upload` під `.RequireAuthorization()`
- [x] `OnRedirectToLogin` → 401 замість 302: дефолт cookie-схеми редіректить на сторінку
      логіну, і `fetch()` прочитав би HTML як успіх
- [x] Хеш пароля — PBKDF2 через `PasswordHasher<T>` (є у фреймворку, без NuGet).
      Генерація: `dotnet run -- hash-password <пароль>`, зберігання — user-secrets
- [x] Форма логіну на фронтенді, кнопка Sign out, перевірка сесії на старті
- [x] Прибрано `/weatherforecast`
- [x] Перевірено вручну (curl через Vite proxy): без cookie `me` і `upload` → 401;
      невірний пароль → 401; вірний → 200 + `Set-Cookie ... samesite=lax; httponly`;
      з cookie `me` і `upload` → 200; logout → 204, далі `me` → 401.
      Ліміт: 4 невдалі → вдалий вхід (200, спробу не витратив) → 5-та невдала 401 →
      6-та 429; вірний пароль при вичерпаному ліміті теж 429
- [ ] `ForwardedHeaders` потрібен ще й для ліміту: за проксі всі запити приходять
      з однієї адреси, і поділ по клієнтах перестає працювати

- [ ] **Повернути хешування пароля перед деплоєм.** Рішення від 2026-09-06: на час
      локальної розробки пароль лежить відкритою константою `OwnerPassword` у
      `Program.cs`. Отже він у git і залишиться в історії — цей самий рядок у прод
      їхати не може. Повернути треба: `PasswordHasher<T>` (PBKDF2), хеш у конфізі
      (`Auth:PasswordHash`), CLI-команду `dotnet run -- hash-password` для генерації,
      і порівняння в постійному часі замість `string.Equals`.
      У user-secrets хеш від `dev-local-password` лишився — не використовується
- [ ] Автотести замість ручної перевірки: xUnit + `WebApplicationFactory`
- [ ] 401 під час upload не скидає фронт у стан «не залогінений» — сесія протухла,
      а користувач бачить помилку завантаження. Потрібен спільний обробник 401
- [ ] GitHub OAuth як друге джерело identity (allow-list на один акаунт)
- [ ] Антифоргері: `.DisableAntiforgery()` лишається на upload. `SameSite=Lax` не пускає
      auth-cookie на cross-site POST, тож зараз дірки немає — переглянути, якщо фронт
      і API колись роз'їдуться на різні адреси

## Інфраструктура і деплой

Схема (рішення від 2026-09-06): бекенд у хмарі — **stateless**, байти файлів
лишаються фізично на домашньому ПК, браузер ходить за ними напряму.

```
Браузер ──статика──► Cloudflare Pages
        ──API───────► Render (ASP.NET у Docker)
        ──байти─────► домашній ПК: Garage (S3) за тунелем
```

### Файловий сервер удома

- [ ] Підняти **Garage** у Docker (S3-сумісний, Rust, під self-host).
      Не MinIO: community-репозиторій архівовано в лютому 2026 — без патчів безпеки
- [ ] Дані — у volume на диску, щоб переживали перезапуск контейнера
- [ ] Тунель для публічного HTTPS: **Tailscale Funnel** (`*.ts.net`, домен не потрібен)
      або Cloudflare Tunnel (потребує власного домену на їхніх NS)
- [ ] Ключі доступу (access key / secret) — у змінних оточення Render
- [ ] **CORS на самому бакеті** — окремий конфіг Garage, не `AddCors` у ASP.NET.
      Браузер вантажить на інший origin, і дозвіл видає сховище. Класичне місце,
      де застрягають
- [ ] Фронт має пережити недоступність сховища: ПК вимкнено → API живий і віддає
      списки, а байти не тягнуться

### Абстракція сховища

- [ ] `IAssetStorage` + дві реалізації: `LocalFileAssetStorage` (dev, як зараз)
      і `S3AssetStorage` (`AWSSDK.S3`). Перемикання — реєстрацією в DI за конфігом
- [ ] Прибрати захардкоджений `ContentRootPath` з `Program.cs`
- [ ] Endpoint видачі presigned URL замість прийому файлу через бекенд —
      Render не проксує байти, лише підписує посилання
- [ ] Той самий код має працювати з Cloudflare R2 без правок: якщо тримати ПК
      увімкненим набридне, міняється лише endpoint і ключі

### Бекенд у хмарі

- [ ] Multi-stage `Dockerfile`: `sdk:8.0` збирає, `aspnet:8.0-alpine` виконує.
      Render не має нативного .NET-рантайму — тільки Docker
- [ ] Kestrel слухає порт зі змінної `PORT` (Render передає свій)
- [ ] `ForwardedHeaders` **перед** `UseHttpsRedirection` — за проксі інакше
      виходить цикл редіректів
- [ ] **Персистувати ключі Data Protection.** Ними шифрується вміст auth-cookie,
      за замовчуванням вони лежать на диску — а диск Render ефемерний. Наслідок:
      кожен деплой розлогінює. Виглядає як плаваючий баг, а це конфігурація
- [ ] Віддача зібраного фронту з ASP.NET (`UseStaticFiles` + fallback на `index.html`) —
      тепер **передумова авторизації**, а не косметика: одна адреса означає, що cookie
      одразу налаштовуються в остаточному вигляді. CORS у проді не потрібен узагалі
- [ ] Якщо колись фронт і API роз'їдуться на різні адреси — список дозволених origin
      брати з конфігу, не хардкодити (актуально лише для того сценарію)
