      login → список → upload (`201`, `Location`) → скачування (байти ті самі) →

## Інфраструктура і деплой

Схема (рішення від 2026-09-06): бекенд у хмарі — **stateless**, байти файлів
лишаються фізично на домашньому ПК, браузер ходить за ними напряму.

```
Браузер ──статика──► Cloudflare Pages
        ──API───────► Render (ASP.NET у Docker)
        ──байти─────► домашній ПК: Garage (S3) за тунелем
```

### Файловий сервер удома

- [x] Підняти **Garage** у Docker (S3-сумісний, Rust, під self-host).
      Не MinIO: community-репозиторій архівовано в лютому 2026 — без патчів безпеки.
      `infra/garage/`: compose з образом `dxflrs/garage:v2.3.0`, `garage.toml`,
      секрети в `.env` поза git, bootstrap-команди в `README.md`.
      Порти 3900/3903 прив'язані до `127.0.0.1` — назовні нічого не стирчить,
      поки перед Garage не поставлено тунель. Бакет `knowledgebase-assets`,
      ключ `knowledgebase-backend` з правами RW.
      `rpc_secret`/`admin_token` навмисне в env, а не у файлі конфігу: bind-mount
      на Windows виглядає для Garage world-readable, і він відмовляється стартувати.
      `root_domain` у `[s3_api]` не заданий — vhost-style вимагає wildcard-DNS,
      якого жоден тунель не дає, отже лишається тільки path-style.
      Перевірено round-trip'ом через одноразовий `amazon/aws-cli`: put → list → get,
      файл побайтово той самий
- [x] Дані — у volume на диску, щоб переживали перезапуск контейнера. Перевірено
      сильнішим тестом, ніж restart: `docker compose down` + `up` (контейнер
      створюється наново) — об'єкт на місці
- [x] Тунель для публічного HTTPS: **Tailscale Funnel** (`*.ts.net`, домен не потрібен).
      Cloudflare Tunnel відкинуто: вимагає власного домену на їхніх NS і має ліміт тіла
      запиту 100 МБ на Free. `tailscale funnel --bg 3900` →
      `https://rospc.tail11818d.ts.net` (443) → `127.0.0.1:3900`. Прив'язку Garage до
      loopback не чіпали — Funnel ходить із того самого хоста.
      Дозвіл вмикається атрибутом вузла (`nodeAttrs` + `funnel`) у політиці tailnet:
      візуальний редактор правил його не показує, тільки JSON editor. Плюс
      HTTPS Certificates на сторінці DNS.
      Перевірено ззовні: без ключів → 403 (відповідає Garage, а не тунель); put/list з
      ключами → працює; **presigned GET → 200 і побайтово той самий файл**, тобто Funnel
      не підміняє `Host`, на якому тримається підпис SigV4.
      Хостнейм публічний і знаходиться через Certificate Transparency — захист сховища
      тримається виключно на ключах
- [x] Окремий ключ для прода — `knowledgebase-render` (RW на бакет), щоб у хмарі був не
      той самий ключ, що в локальному `appsettings.Local.json`: відкликаються нарізно
- [x] Ключі доступу (access key / secret) — у змінних оточення Render
      (`Storage__Provider=S3`, `Storage__S3__*`). Сховище на проді працює — за словами
      користувача (2026-09-07): upload на `knowledgebase-9z29.onrender.com` доходить
      до Garage. Тобто `S3AssetStorage` підтверджено не лише проти локального Garage,
      а й у зв'язці Render → Tailscale Funnel → домашній ПК
- [ ] **CORS на самому бакеті** — окремий конфіг Garage, не `AddCors` у ASP.NET.
      Браузер вантажить на інший origin, і дозвіл видає сховище. Класичне місце,
      де застрягають
- [ ] Фронт має пережити недоступність сховища: ПК вимкнено → API живий і віддає
      списки, а байти не тягнуться

### Абстракція сховища

- [x] `IAssetStorage` + `LocalFileAssetStorage` — інтерфейс і локальна реалізація за ним,
      зареєстровані в DI (singleton: теку створює конструктор, щоб паралельні перші
      завантаження не гонились). Ендпоінт більше не знає про файлову систему — віддає
      `Stream` і отримує `StoredAsset`. Перевірено реальним завантаженням: 200 і файл
      під GUID у `data/assets`
- [x] `S3AssetStorage` (`AWSSDK.S3` 4.0.102.5) другою реалізацією; перемикання —
      `Storage:Provider` = `Local` | `S3`, одним `if` у `StorageRegistration`.
      Ключі — лише через змінні оточення / user-secrets (`Storage__S3__AccessKeyId`);
      неповний конфіг валить застосунок на старті (`ValidateOnStart`), а не на першому
      завантаженні у вигляді 500. Іменування файлу винесено в `AssetFileName`, щоб
      `SafeExtension` не дублювався у двох реалізаціях.
      **Пастка AWS SDK v4:** дефолт `RequestChecksumCalculation = WHEN_SUPPORTED`
      перетворює PUT на chunked-тіло з трейлером контрольної суми, і Garage відповідає
      `Invalid payload signature`. Виставлено `WHEN_REQUIRED` у конфізі клієнта.
      Перевірено проти локального Garage: логін → upload → 200, об'єкт у бакеті
      побайтово збігається з надісланим; порожній файл → 400, без cookie → 401;
      `Provider=Local` поводиться як раніше
- [x] Локальні налаштування — `backend/appsettings.Local.json` (`UseLocalOverrides`):
      у `.gitignore` і `.dockerignore`, підключається **лише в Development**. Джерело
      додається після `CreateBuilder`, тому перебиває всі інші, включно зі змінними
      оточення — гейт на Development саме для цього: копія, що осіла поруч із
      бінарником, не перебʼє конфіг Render. Перевірено: ключі Garage лежать у файлі,
      `Storage__Provider=S3 dotnet run` вантажить у бакет без жодної змінної з ключами;
      без цієї змінної файли лягають у `data/assets`, як раніше; той самий файл поруч
      із бінарником у Production ігнорується (падіння на `ValidateOnStart`);
      `docker build` не бачить його в контексті (перевірено пробним образом)
- [ ] Content-Type у S3 виводиться SDK з розширення ключа, а не з того, що прислав
      клієнт: `IAssetStorage.SaveAsync` його не приймає. Для `.pdf` вийшло правильно,
      але файл без розширення браузер отримає як `application/octet-stream`.
      Віддача байтів уже є і вгадує тип так само — з розширення
- [ ] Оригінальне ім'я файлу і його MIME-тип ніде не зберігаються: `upload` віддає їх

### Бекенд у хмарі

- [x] Multi-stage `Dockerfile` у корені репо: `node:24-alpine` збирає фронт,

      за замовчуванням вони лежать на диску — а диск Render ефемерний. Наслідок:
      кожен деплой розлогінює. Виглядає як плаваючий баг, а це конфігурація.
      На Free полагодити нічим: **диски доступні лише на платних інстансах.**
      Або платний план і `PersistKeysToFileSystem` на змонтований диск, або живемо
      з розлогіном після кожного деплою.
      Підтверджено на локальному контейнері. Сам ASP.NET пише про це в лог на старті:
      `Storing keys in a directory '/root/.aspnet/DataProtection-Keys' that may not be
      persisted outside of the container`. Перезапуск **того самого** контейнера
      (`docker restart`) сесію зберігає — ключі лежать у його шарі; а на **новому**
